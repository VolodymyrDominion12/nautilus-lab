# 25. Крос-секційний momentum і ворота допуску

Статус: **кандидат**, виміру на реальних даних ще немає. Цей документ фіксує
гіпотезу, протокол перевірки і пороги **до** першого прогону — щоб планку не можна
було підігнати під результат.

## 1. Гіпотеза

Мажорні монети рухаються разом, але капітал між ними ротується: монети, що лідирували
останні кілька тижнів, схильні лідирувати й далі. Робот ранжує кошик за минулою
дохідністю, тримає `top_n` найсильніших і переранжовує кожні `rebalance_every` барів.

Дві страховки відносно підручникової версії:

- **`skip_bars=1`** — останній бар не входить у рахунок: короткий рух схильний
  розвертатися і домінував би в рейтингу.
- **Фільтр абсолютного momentum** — монета тримається лише з додатним власним
  momentum. У загальному обвалі всі монети «ранжуються», а фільтр переводить кошик у
  кеш замість того, щоб тримати його до дна.

Лише лонг, спот, без плеча: сума ваг ≤ 1. Порожні слоти — кеш.

Код: `domain/xsmom.py` (правило), `application/xsmom_backtest.py` (симулятор),
`application/run_xsmom.py` (walk-forward і аудит).

## 2. Чому окремий симулятор, а не рушій Nautilus

Решта роботів торгують один інструмент або пару через `NautilusResearchBacktest`.
Ротація по N монетах потребує мульти-інструментної стратегії в Nautilus; поки її
немає, симулятор тримає ті самі правила:

| Правило | Як |
|---|---|
| Без lookahead | Вага вирішується на close бару *t*, виконання на open бару *t+1* |
| Комісії | Taker з `FeeSchedule` на кожен торгований ноціонал |
| Прослизання | `--slippage-bps` (за замовчуванням 5 bps) проти нас на кожному філі |
| Без плеча і шортів | Спершу продажі, потім купівлі; купівлі масштабуються, якщо бракує кешу |
| Marked equity | Крива = кеш + позиції за close; просадка бачить відкриті збитки |
| Прогрів | Бари перед вікном лише рахують рейтинг, не торгуються |

Тест `test_future_bars_never_change_the_past` закріплює відсутність lookahead:
обрізання майбутніх барів не змінює жодної точки кривої в минулому.

## 3. Протокол

```bash
# денні бари: інтервал ingest бере з BAR_INTERVAL
BAR_INTERVAL=1d uv run lab ingest --symbols BTCUSDT,ETHUSDT,SOLUSDT,BNBUSDT,XRPUSDT,ADAUSDT,DOGEUSDT --start 2020-01-01
uv run lab xsmom --interval 1d --folds 6 --pbo
```

- 6 ковзних фолдів; параметри заново обираються на in-sample кожного фолду.
- Сітка навмисно мала: `lookback ∈ {14, 30, 60}`, `top_n ∈ {2, 3}`, `rebalance = 7`
  (6 конфігурацій). Кожна зайва конфігурація — ще одна спроба, яку дисконтує DSR.
- Метрика відбору — `calmar` (дохідність / максимальна просадка), не сирий PnL.
- Планка — рівновагий buy&hold **того самого кошика** за ті самі бари. Ротація
  має сенс, лише якщо обганяє просте утримання всіх монет.

## 4. Ворота допуску (`application/promotion_gate.py`)

Однакові для всіх роботів. Кожна перевірка — PASS, FAIL або NOT MEASURED; робот
проходить лише тоді, коли всі перевірки виміряні й пройдені.

| Перевірка | Поріг | Джерело |
|---|---|---|
| Кількість фолдів | ≥ 6 | `--folds` |
| Прибуткові фолди після комісій | ≥ 83% (5 з 6) | `--folds` |
| Середній OOS проти buy&hold | більший | `--folds` |
| OOS-угоди | ≥ 30 | `--folds` |
| PBO | ≤ 0.3 | `--pbo` |
| DSR | ≥ 0.95 | `--pbo` |

`lab research --folds N` бачить лише першу половину доказів, тож у кращому разі друкує
`promotion_gate=INCOMPLETE`; `lab xsmom --pbo` бачить обидві.

Проходження воріт — це дозвіл на **30 днів paper**, а не на live. `lab live`
лишається fail closed.

## 5. Що далі, якщо кандидат пройде

1. Адаптер мульти-інструментної стратегії для Nautilus, щоб paper ішов тим самим
   рушієм, що й решта роботів.
2. Paper 30 днів: результат має лягти в розподіл OOS-фолдів.
3. Лише після цього — окреме рішення про live з окремими ключами.

Якщо не пройде — рядок `❌ rejected` у `research/journal.md` з числами. Це теж
результат.
