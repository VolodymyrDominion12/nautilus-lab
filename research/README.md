# research/ — офлайн-контур дослідження

Тут живе все, що робить модель **поза** торговим циклом: промпти, запропоновані
гіпотези та журнал рішень. Ніщо з цієї теки не виконується під час бектесту чи
торгівлі. Деталі й обґрунтування — [docs/14-llm-model-u-torhivli.md](../docs/14-llm-model-u-torhivli.md).

```
research/
├── README.md            ← цей файл
├── prompts/             ← шаблони промптів (01 запускається CLI, 02–03 — вручну)
├── hypotheses/          ← артефакти: одна модель-відповідь = один JSON-файл
├── journal.md           ← журнал рішень: прийнято / відкинуто і чому
└── journal.jsonl        ← машинний лог тих самих рядків (з'являється після першого --journal)
```

## Два контури

| | Гарячий шлях | Офлайн-контур (ця тека) |
|---|---|---|
| Що | Nautilus, `on_bar`, ризик, ордери | промпти, модель, рев'ю, журнал |
| Час | мілісекунди | хвилини |
| LLM-виклик | **ніколи** | норма |
| Артефакт | `Signal` | файл у git → рев'ю людини → код у `domain/` |

Якщо LLM-виклик виконується під час прогону бектесту — це баг, навіть якщо
результат гарний.

## Цикл

```
промпт (prompts/01)  →  модель  →  hypotheses/*.json  →  рев'ю людини
                                                              │
                        journal.md  ←  рішення  ←──────────────┘
                              │
                    domain/<robot>.py + tests  →  purged CV  →  walk-forward OOS
```

## Команди

Файл `prompts/01-generate-alphas.md` — це **чистий промпт**, який іде в модель.
Скрипт підставляє в нього три плейсхолдери: перелік 12 ознак, кількість гіпотез
і дату відсічення. Якщо хоч одного плейсхолдера в шаблоні немає — команда падає,
а не шле напів-промпт у модель.

```bash
# Подивитись, який промпт піде в модель (мережі не торкається, ключ не потрібен)
uv run lab propose --dry-run

# Спитати модель і записати артефакт (потрібен LLM_API_KEY у .env)
uv run lab propose --count 5 --as-of 2026-09-15

# Інша модель або локальний сервер відкритих ваг (безпека даних)
uv run lab propose --base-url http://127.0.0.1:11434/v1 --model qwen2.5:14b

# Те саме через скрипт — він лише переадресовує в `lab propose`
.venv/bin/python scripts/propose_alphas.py --count 5
```

Коди виходу: `0` — успіх, `1` — помилка (конфіг, непридатний артефакт, збій ендпоінта).
Без `LLM_API_KEY` команда **падає закрито** і нічого не вигадує замість моделі.
Якщо `uv` не має доступу до свого кеша — `.venv/bin/lab propose …`.

## Журнал рішень

Кожен прогін або пропозицію можна записати в журнал одним прапорцем `--journal`:

```bash
uv run lab research --robot regime --folds 4 --journal
uv run lab propose --count 5 --journal
```

Що відбувається:

- у `journal.md` дописується рядок людської таблиці (дата, джерело, ворота, OOS,
  buy&hold, рішення, причина);
- у `journal.jsonl` дописується той самий рядок як JSON — для машинного аналізу,
  разом із полем `provenance`: git-ревізія (і чи було дерево «брудним»), хеш `uv.lock`,
  версія NautilusTrader, хеш ефективних налаштувань (`.env` + змінні оболонки, без
  секретів) і відбиток каталогу. Той самий `manifest rev=...` рядок `lab research`
  друкує першим; `manifest_warning=...` у stderr означає, що ревізія сама цей прогін
  не відтворить (docs/27 E-1.4);
- існуючі рядки **не переписуються**, тому твоє рішення в старому рядку переживе
  наступний прогін;
- у колонку `OOS` ніколи не потрапляє in-sample число: без OOS-спліту там `n/a`,
  а цифра йде в «Причину» з поміткою `(not an OOS number)`.

Типово вимкнено; щоб увімкнути для всіх прогонів — `JOURNAL_ENABLED=true`.
Якщо маркери `journal:rows:start/end` у файлі зникли, команда завершується кодом 1.


## Що робити з артефактом

1. Прочитати `hypotheses/*.json` — там `hypotheses[]` і блок `review` зі `status: pending`.
2. Відкинути все, у чого немає економічного механізму або є `unknown_identifiers`
   (вигадана фіча — типова помилка моделі).
3. Реалізувати прийняте в `domain/` за [docs/07](../docs/07-yak-stvoryty-strategiyu.md).
4. Прогнати ворота: `pytest` → `ruff` → `mypy src tests` → purged K-fold.
5. **Зареєструвати тест до прогону** (docs/27 R-2, [ADR 0008](../docs/adr/0008-poperednia-reiestratsiia-testu.md)):
   `lab research --robot <robot> --folds N --register "що має показати OOS і чому"`.
   Команда рахує вікна фолдів, нічого не запускаючи, і пише умови з хешем у
   `research/preregistrations/`. Закомітити файл.
6. `lab research --robot <robot> --folds N` з тими самими параметрами (це і є OOS). Рядок
   `preregistration=matched` означає, що умови збіглися; без цього гейт не дасть PROMOTE.
7. Записати рядок у [journal.md](journal.md): що перевірили, яке число, рішення, причина.

## Чого не робити

- **Не показувати моделі OOS-результат і не просити «покращити».** Так OOS стає
  частиною підбору (docs/07, §1).
- **Не питати про конкретні історичні події.** Модель навчена на даних до свого
  cutoff і пам'ятає, чим закінчилась історія, на якій ти збираєшся її перевіряти.
  Це найнебезпечніша пастка цього контуру (docs/14, §6.1).
- **Не запускати згенерований код із реальними ключами.** `lab live` fail closed —
  і це не можна «тимчасово обійти».
- **Не вірити переконливому поясненню.** Артефакт — це гіпотеза, а не результат.
- **Не перереєстровувати тест після поганого результату.** Нова реєстрація з ширшою
  сіткою чи іншою кількістю фолдів — це нова спроба; її рахує журнал спроб
  (`research/trials.jsonl`), і DSR стає суворішим.
