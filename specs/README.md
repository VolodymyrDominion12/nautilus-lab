# specs/ — специфікації nautilus-lab

Тут лежать специфікації, які **звіряються з кодом**, а не просто описують його.

## Навіщо це

Специфікація, яка розійшлася з кодом, гірша за відсутню: вона впевнено бреше.
У цьому проєкті так уже траплялося — `docs/05` і `docs/10` стверджували, що до
рушія підключено 3 роботи, коли в коді їх 5. Тому кожне поле, яке можна
перевірити машинно, перевіряється:

| Поле | Проти чого звіряється |
|---|---|
| `name` | значення `RobotName` |
| `implementation.wired_in_backtest` | членство в `BACKTEST_WIRED_ROBOTS` |
| `implementation.minimum_bars` | `minimum_bars()` |
| `implementation.grid_source` | наявність гілки в `param_grid.py` |
| `implementation.domain_module` | файл/тека існує |
| `implementation.strategy_class` | клас існує в домені або в адаптері |
| `params[].env` | поле класу `Settings` |
| `component.invariants[].verified_by` | тест справді існує |

## Запуск

```bash
.venv/bin/python specs/_validator.py              # усі спеки, детально
.venv/bin/python specs/_validator.py regime       # одна
.venv/bin/python specs/_validator.py --quiet      # лише підсумок
uv run pytest tests/unit/test_specs.py -v         # те саме + покриття, у pytest
```

Валідатор читає код через `ast` — **без імпорту проєкту**. Це навмисно: він не
має побічних ефектів (не читає `.env`, не тягне `nautilus_trader`) і працює
навіть коли залежності зламані — а саме тоді перевірка найпотрібніша.

## Структура

```
specs/
├── _schema.yaml          мета-схема: обов'язкові поля, статуси, що звіряється
├── _validator.py         ОДНА реалізація перевірок для CLI і для тестів
├── strategies/           по одній спекі на кожне значення RobotName
│   └── regime.yaml       ← ЕТАЛОН, з якого варто копіювати
└── components/           наскрізні механізми (ризик, walk-forward, аудит…)
```

`_validator.py` навмисно один і для командного рядка, і для pytest: дві
реалізації перевірок неминуче розійшлися б між собою, і тоді «зелений CLI» та
«зелені тести» означали б різні речі.

## Життєвий цикл статусу

| Статус | Що означає |
|---|---|
| `candidate` | специфіковано, код є, рішучого виміру немає |
| `validated` | **виміряно перевагу**: OOS обганяє buy&hold за той самий період |
| `rejected` | виміряно, переваги немає — гіпотезу закрито (`rejection_reason` з числами) |
| `blocked` | доменний код є, адаптера виконання немає → мусить падати fail closed |

Станом на зараз **жоден робот не має статусу `validated`** — за `README.md` і
`docs/05` жоден не обганяє buy&hold. Це задокументований результат проєкту, і
специфікації роблять його видимим, а не приховують.

`candidate` і `rejected` — принципово різні: «не доведено» проти «доведено, що
не працює». Плутанина між ними або передчасно ховає живого робота, або змушує
нескінченно повертатися до мертвої ідеї.

## Головна пастка, яку ловить валідатор

`application/param_grid.py` має власні гілки сітки лише для `pairs`,
`vpin_momentum`, `formulaic_lgbm` і `ema`. **Усі інші** роботи провалюються в
останній блок — сітку `regime`. Тож новий робот без гілки підбирає параметри
**чужої** стратегії й виглядає так, ніби працює.

Тому `implementation.grid_source` обов'язкове (`explicit` / `default_branch`) і
звіряється з кодом.

## Як додати робота

1. Створи `specs/strategies/<robot>.yaml` за зразком `regime.yaml` — **до** коду.
2. `.venv/bin/python specs/_validator.py <robot>` — нуль помилок.
3. Реалізуй робота (ланцюг реєстрації описано в
   `.agents/skills/spec-driven-development/SKILL.md`).
4. Онови спеку під фактичні `grid`, `minimum_bars`, `grid_source`.
5. `uv run pytest tests/ -q`.

Якщо робота додано в `RobotName` без спеки — впаде і валідатор, і
`test_every_robot_has_a_spec`. Це навмисно: `spec before code`, перевірене машиною.
