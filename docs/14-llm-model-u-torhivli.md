# 14. Як LLM/LRM-модель може допомогти в біржовій торгівлі на крипторинках

Це практичне доповнення до [13-ai-2026-vidpovidnist.md](13-ai-2026-vidpovidnist.md).
Там — мапа «розділ статті → файл у коді». Тут — відповідь на інше питання:
**що конкретно дає велика міркуюча модель (LRM/LLM класу DeepSeek-R1, описана в
[ШІ-документі](../Алгоритми%20ШІ%20У%20Криптоторгівлі%202026%20(1).md)) у торгівлі на криптобіржі** —
і чого вона не дає.

---

## 0. Про яку саме «модель» мова

У слові «модель» тут змішуються три різні речі. Їх треба розділити, бо плутанина
веде до хибних очікувань.

| Що це | Приклад | Роль у торгівлі | Стан у lab |
|-------|---------|-----------------|------------|
| **LRM/LLM-помічник** | DeepSeek-R1, дистиляти, будь-який агент-асистент | аналітик та інженер **поза** гарячим шляхом | 🔴 інтеграції немає (і не треба в рантаймі) |
| **ML-модель сигналу** | LightGBM на формульних ознаках | видає напрямок на **закритому** барі | ✅ робот `formulaic_lgbm` (потрібен `FORMULAIC_MODEL_PATH`) |
| **Статистична модель ризику / мікроструктури** | VPIN, Хоукс, O-U, коінтеграція | фільтр режиму, розмір позиції, ворота входу | ✅/🟡 див. [13 §7](13-ai-2026-vidpovidnist.md) |

Далі — переважно про **першу**. Саме її «розхвалює» стаття, і саме вона в цьому репо
поки що не використовується жодним рядком коду (перевірено: у `src/` немає жодного
клієнта LLM).

**Головна теза одразу.** LLM не передбачає ціну. Вона не має edge. Вона **стискає цикл
дослідження**: гіпотеза → код → тести → бектест → розбір → документація. Edge
народжується не в моделі, а у воротах, через які проходить її результат.

---

## 1. Головне архітектурне правило: два контури

Стаття описує LLM як компонент генерації альф — і це правильно, **але тільки в
офлайн-контурі**. Розділення контурів — не стилістика, а умова відтворюваності.

| | **Гарячий шлях** | **Офлайн-контур** |
|---|---|---|
| Що там | Nautilus engine, `on_bar`, розмір позиції, ордери | дослідження, генерація коду, рев'ю, звіти |
| Час | мілісекунди | хвилини–години |
| Хто всередині | детермінований код на `Decimal` | LLM + людина |
| LLM-виклик | ❌ ніколи | ✅ норма |
| Артефакт | `Signal` | файл у git (формула, `.py`, `.txt` бустера, звіт) |
| Ворота | ризик-шар, fail-closed | тести → purged CV → walk-forward OOS → buy&hold |

**Чому LLM не можна в `on_bar`:**

1. **Затримка.** Секунди проти мілісекунд — на 1h-барах це ще «терпимо», але саме цим
   ламається будь-яка ідея MFT/HFT зі статті.
2. **Недетермінізм.** Той самий вхід → різний вихід. Бектест стає невідтворюваним,
   тобто безглуздим.
3. **Ціна.** Кожен бар × кожен інструмент = рахунок за токени, який нічим не
   виправданий.
4. **Відсутність гарантій.** Модель може «вирішити» не торгувати або вигадати
   неіснуючий метод API — і жоден тест цього не спіймає, бо немає фіксованого артефакту.
5. **Підгляд.** Див. §6.1 — найнебезпечніша пастка саме цього підходу.

Правило, яке варто записати в код-рев'ю: **якщо рядок коду викликає LLM і цей рядок
виконується під час прогону бектесту — це баг**, навіть якщо результат гарний.

## 2. Дев'ять ролей, де модель дає реальну користь

### 2.1. Генерація гіпотез і формульних альф

**Що робить.** Пропонує комбінації наявних примітивів і формулює, *чому* вони мали б
працювати — модель сильна саме в побудові ланцюжка «причина → механізм → ознака».

**У цьому репо.** `FormulaicAlphaEngine` (`domain/formulaic_alphas.py`) уже рахує
12 фіч: `ret`, `ret_5`, `vol_10`, `volume_ratio`, `close_loc`, `momentum_10`,
`reversal_3`, `vol_of_vol`, `trend_er`, `range_pct`, `high_low_spread`, `vol_20`.
Тому промпт має вимагати: **комбінуй лише ці 12**, жодних нових API — інакше модель
почне вигадувати методи, яких не існує (див. §6.2).

**Що модель НЕ робить.** Не перевіряє. Кожна гіпотеза йде у ворота:
`scripts/train_formulaic_lgbm.py` (purged K-fold, типово 5 фолдів, embargo 10) →
`lab research --robot formulaic_lgbm --folds 4`.

**Формат відповіді** (обов'язковий, інакше результат не автоматизується):
ім'я, формула в термінах наявних фіч, економічний механізм, горизонт у барах,
очікуваний знак, **що вб'є ідею**.

### 2.2. Гіпотеза → код робота за існуючим контрактом

**Що робить.** Пише `domain/<robot>.py`, юніт-тести, гілки в `param_grid.py`,
змінні в `.env.example`, оновлює `RobotName`.

**У цьому репо.** Контракт жорсткий і вже описаний у
[07-yak-stvoryty-strategiyu.md](07-yak-stvoryty-strategiyu.md) §2 — це ідеальний
вхід для LLM: замість «напиши стратегію» даємо їй таблицю «куди саме додавати код» і
7 правил. Модель тут — прискорювач рутини, не автор ідеї.

**Ворота.** `uv run pytest`, `ruff check`, `mypy src tests`. Особливо правило 3 з
docs/07 — **тільки закриті бари**. Це те, що LLM порушує найчастіше.

### 2.3. Дизайн експерименту й дисципліна out-of-sample

**Що робить.** Допомагає вибрати горизонт, embargo, кількість фолдів, метрику;
нагадує про multiple testing.

**У цьому репо.** Механіка вже є: walk-forward з розривом-embargo, `--folds N`
(кілька ковзних фолдів замість одного числа з однієї ділянки історії), Optuna TPE
(`--optuna --trials N`). Модель тут корисна як «рецензент плану», а не як джерело
параметрів.

**Ключове правило (docs/07 §1):** побачив поганий OOS → змінив параметри → запустив
знову — OOS більше не out-of-sample. Якщо в промпті є слова «ось OOS-результат,
покращ», ти щойно перетворив OOS на in-sample.

### 2.4. Рев'ю коду на підгляд у майбутнє (lookahead)

**Найцінніша технічна роль моделі.** Вона непогано ловить типові патерни:

| Патерн | Що це |
|--------|-------|
| `shift(-n)`, `.iloc[i+1]` | читання майбутнього барa |
| центроване вікно (`rolling(center=True)`, `np.convolve(..., 'same')`) | у ознаку потрапляє майбутнє |
| `max()` / `min()` / `mean()` по всьому ряду | статистика, якої на момент барa ще не існувало |
| scaler / нормалізація, навчені на всій вибірці | витік розподілу з майбутнього |
| ресемпл із `label='right'` без зсуву | бар «знає» свій закритий стан заздалегідь |
| `ffill()` після `reindex` | протягування майбутнього значення назад |
| таргет, що випадково лишився серед фіч | прямий витік мітки |

**У цьому репо.** Домен уже побудований на `RollingWindow` без підгляду, і це варто
казати моделі прямо: «перевір, що новий код не виходить за межі `RollingWindow`».
Рев'ю **доповнює** тести, а не замінює: `pytest` ловить падіння, а не статистичний
витік.

### 2.5. Розбір результатів бектесту й тиршита

**Що робить.** Читає вивід `lab research` і HTML-тиршит і ставить незручні питання:
де саме з'їдаються гроші.

**Що шукати разом з моделлю:**

- **Оборот × комісія проти edge.** Стаття наводить цифру річного обороту 185% для
  DRL-агента, оптимізованого лише на прибутковість, і падіння Sharpe нижче 1.0 через
  slippage. У lab це вимірюється: `MAKER_FEE`/`TAKER_FEE` = 0.001, затримка 50 мс,
  імовірнісне проковзування. Тобто висновок статті тут **перевіряємо**, а не віримо.
- **Концентрація.** Весь прибуток в 1–2 угодах — це не edge, це лотерея.
- **Розрив IS/OOS.** In-sample завжди гарний; дивитись тільки на OOS.
- **Чутливість до параметрів.** Плато чи голка? Голка = перенавчання.
- **Час у позиції й розподіл угод по годинах доби** — крипта має добову структуру.

### 2.6. Ризик-шар як окремий співрозмовник

**Що робить.** Перевіряє арифметичну узгодженість лімітів — те, де людина помиляється
найчастіше.

**У цьому репо** дефолти: `RISK_PER_TRADE=0.005`, `STOP_PCT=0.01`,
`MAX_DAILY_LOSS=0.02`, `MAX_DRAWDOWN=0.06`, `MAX_OPEN_POSITIONS=1`. Звідси прості
наслідки, які корисно проговорити з моделлю:

- ризик 0.5% при стопі 1% ⇒ номінал позиції ≈ 50% капіталу;
- денний ліміт 2% ÷ 0.5% на угоду = **4 збиткові угоди поспіль** до зупинки входів;
- просадка 6% = **12** збиткових угод поспіль — і це не «хворе», це штатна
  послідовність при win rate ~50%.

Opt-in оверлеї (`USE_VOL_SCALING`, `USE_FRACTIONAL_KELLY`, `USE_CVAR_BREAKER`)
модель допомагає не «ввімкнути», а **прочитати, що вони зробили з розподілом
результатів** — це головне питання, на яке бектест відповідає.

### 2.7. Нестаціонарність і деградація

**Що робить.** Складає регламент обслуговування робота: коли переоцінювати, коли
вимикати.

**У цьому репо** це вже частково реалізовано: `PAIRS_REFIT_EVERY=24` — переоцінка
коінтеграції раз на добу на 1h-барах, з закриттям позиції, якщо зв'язок зникнув;
`domain/kill_switch.py` — аварійна зупинка. Модель корисна як автор **чекліста
деградації**: які метрики дивитись, який поріг вважати поломкою, що робити між
«вимкнути» і «дочекатись».

Стаття тут дає чесну рамку: те, що давало 60% точності тижнем раніше, може деградувати
до 51% — не через баг, а через regime shift.

### 2.8. Зовнішній контекст (новини, ончейн, регуляторика)

**Що робить.** Стискає великі текстові масиви в структуровані поля.

**Критично важливо:** тільки офлайн, батчами, з **фіксованою датою відсічення** в
промпті («уяви, що сьогодні 2026-03-01, не використовуй нічого, що стало відомо
пізніше»). Інакше модель «пригадає» реальні події — і ти отримаєш сигнал, який у
бектесті виглядає геніально, а в житті не існує (§6.1).

**Поза скоупом lab:** on-chain execution, Uniswap v4 hooks, MEV, TEE — див.
[13 §5](13-ai-2026-vidpovidnist.md). Тут lab — Binance spot/perp research.

### 2.9. Документація й пост-мортем

**Що робить.** Перекладає оглядову статтю в мапу «розділ → файл → статус».

**Живий приклад — уже в цьому репо:** [13-ai-2026-vidpovidnist.md](13-ai-2026-vidpovidnist.md)
і цей документ. Користь неочевидна, але реальна: після кожного прогону лишається
слід — що перевірили, чим закінчилось, чому відкинули. Без цього через місяць ти
перевідкриєш ту саму погану ідею.

## 3. Як це виглядало б в архітектурі lab

```
  стаття / ідея / дані
          │
          ▼
 ┌─────────────────────┐     research/prompts/*.md   (промпт + модель + версія)
 │  ОФЛАЙН: LLM        │──── research/hypotheses/*.json
 └─────────────────────┘              │
                                      ▼
                          ┌───────────────────────┐
                          │  людина: апрув ідеї   │  ← обов'язковий шар
                          └───────────────────────┘
                                      │
                                      ▼
                    domain/<robot>.py  +  tests/unit/test_<robot>.py
                                      │
                       pytest → ruff → mypy --strict
                                      │
                                      ▼
              lab research --robot <robot> --folds N     ← OOS, не in-sample
                                      │
                    ┌─────────────────┴─────────────────┐
                    ▼                                   ▼
        reports/*.html (тиршит)              журнал: прийнято / відкинуто і чому
                    │
                    ▼
        ┌─────────────────────┐
        │ ОФЛАЙН: LLM         │ → пост-мортем, оновлення docs/
        └─────────────────────┘

  ══════════════════════════════════════════════════════════════
  ГАРЯЧИЙ ШЛЯХ (бектест і майбутній paper): Nautilus engine.
  Жодного LLM-виклику. LIVE_ENABLED=false, `lab live` fail closed.
```

**Три правила цієї схеми:**

1. **Артефакт, не виклик.** Результат моделі завжди матеріалізується у файл у git.
   Тільки тоді він відтворюваний і рев'юабльний.
2. **Версіонування промпту.** Один і той самий промпт дає різні відповіді. Тому
   зберігаємо разом: текст промпту, назву й версію моделі, дату, вхідні дані.
3. **Людина на апруві.** Модель пропонує — людина вирішує, що потрапляє в `domain/`.

## 4. Три шаблони промптів (готові до використання)

### 4.1. Генерація альфи

```text
Ти — кількісний дослідник. Працюєш з крипто-барами 1h (ETH/USDT, BTC/USDT).

ДОСТУПНІ ОЗНАКИ (використовуй ЛИШЕ ці, не вигадуй нових):
ret, ret_5, vol_10, volume_ratio, close_loc, momentum_10,
reversal_3, vol_of_vol, trend_er, range_pct, high_low_spread, vol_20
(усі рахуються на ЗАКРИТИХ барах; вікно історії 30 барів).

ЗАВДАННЯ: запропонуй 5 гіпотез напрямку руху на горизонті 5 барів.

ОБМЕЖЕННЯ:
- жодних ознак із майбутнього; жодних даних про конкретні історичні події;
- кожна гіпотеза має мати економічний механізм (хто на іншому боці і чому помиляється);
- якщо механізму немає — не пропонуй.

ФОРМАТ: JSON-масив, кожен елемент:
{"name": str, "formula": str, "mechanism": str, "horizon_bars": int,
 "expected_sign": "+1|-1", "kill_condition": str}

Не пиши код. Не оцінюй прибутковість. Не згадуй, що відбувалось на ринку в минулому.
```

### 4.2. Lookahead-рев'ю згенерованого коду

```text
Ти — рецензент коду торгової стратегії. Єдина мета: знайти підгляд у майбутнє
(look-ahead bias) і витік даних.

КОНТЕКСТ ПРОЄКТУ: домен рахує ознаки інкрементально на закритих барах і не має
права читати мережу, .env чи Nautilus. Гроші й ціни — тільки Decimal.

ФАЙЛ: <вставити>

ПЕРЕВІР: shift(-n) та індекси i+1; центровані вікна; статистики по всьому ряду
(max/min/mean/std, scaler, нормалізація); ресемпл без зсуву; ffill/reindex;
використання поточного (незакритого) бару; таргет серед фіч.

ФОРМАТ: список знахідок {"file_line": str, "severity": "high|medium|low",
"what": str, "why_leak": str, "fix": str}. Якщо знахідок немає — так і скажи.

НЕ переписуй код. НЕ пропонуй «покращити» логіку. НЕ коментуй прибутковість.
```

### 4.3. Розбір результатів прогону

```text
Ти — ризик-менеджер. Перед тобою вивід walk-forward бектесту і тиршит.

ВХІД: <вивід lab research + метрики>

ПЛАНКА: buy&hold за той самий OOS-період = <X>%.
ВИТРАТИ: maker/taker 0.1%, затримка 50 мс, імовірнісне проковзування.

ДАЙ:
1. Скільки угод, який оборот, скільки грошей з'їли комісії та проковзування
   (порахуй, якщо є дані; якщо даних немає — скажи яких саме не хватає).
2. Чи прибуток концентрований в 1–2 угодах.
3. Розрив in-sample / out-of-sample і що він означає.
4. Три найімовірніші причини результату.
5. Одну зміну, яку варто перевірити НАСТУПНИМ прогоном.

НЕ пропонуй підбирати параметри під побачений OOS. НЕ оцінюй «перспективність»
ідеї. Пиши лише те, що випливає з наведених чисел.
```

## 5. Як зрозуміти, чи модель справді допомагає

Метрики для самої LLM-практики, а не для стратегії:

| Метрика | Як рахувати | Здоровий орієнтир |
|---------|-------------|-------------------|
| Частка гіпотез, що дійшли до OOS-прогону | прогнано / згенеровано | < 20% — нормально |
| Частка гіпотез, що обігнали buy&hold | прийнято / прогнано | **зараз 0** — і це чесний результат |
| Час від ідеї до OOS-числа | годин на гіпотезу | має падати |
| Підтверджені знахідки lookahead | реальні / заявлені | якщо < 20% — модель «фантазує», переходь на меншу |
| Гіпотези, перевірені без OOS | штук | **мусить бути 0** |
| Вартість токенів на прийняту гіпотезу | $ / прийнята | рахуй, щоб знати порядок величини |

Важливо: **нуль гіпотез, що обігнали buy&hold, — це не провал методу**. У цьому репо
README прямо фіксує, що жоден із трьох роботів планку buy&hold не обганяє. LLM не
змінює ринкову статистику; вона лише дозволяє швидше це з'ясувати й не витратити на
це місяці.

## 6. Пастки, які роблять роботу безглуздою

### 6.1. Temporal leakage з тренувальних даних моделі — пастка №1

LLM навчена на даних до свого cutoff і **знає, що BTC та ETH робили у 2021–2025**.
Якщо попросити «придумай стратегію для ETH за 2024 рік» або «що спрацювало на
пампах 2021-го», модель може видати правило, яке відтворює відомий їй результат —
а не закономірність.

**Захист:**

1. Питати **структуру** («які комбінації ознак описують виснаження ліквідності»), а не
   «що було».
2. Будь-який результат перевіряти на періоді **після** cutoff моделі.
3. Ніколи не питати про конкретні події та дати.
4. Ставити в промпт відсічення: «уяви, що сьогодні <дата>, пізнішого не існує».
5. Пам'ятати: «пройшло бектест» на історичних даних, які модель знала, — це не доказ.

### 6.2. Галюцинації API й фактів

Модель упевнено вигадує параметри NautilusTrader, назви методів, конфігураційні
ключі. Захист: код має **компілюватися й проходити тести**; `mypy --strict` ловить
частину; рев'ю людиною — решту. Ніколи не запускати згенероване з реальними ключами.

### 6.3. Multiple testing: 100 гіпотез → кілька «переможців» випадково

Якщо згенерувати 100 альф, кілька пройдуть ворота випадково. У репо є сітка
параметрів і Optuna, але повного апарату (PBO / CSCV) ще немає —
[13 §6](13-ai-2026-vidpovidnist.md). Захист: обмежений бюджет гіпотез, обов'язковий
економічний механізм, і жодного дотику до OOS під час відбору.

### 6.4. Перенавчання через саму розмову

Найпідступніше: показав моделі OOS-число й попросив покращити — OOS втрачено. Далі
всі «покращення» — це підбір під конкретну ділянку історії. Правило з
[docs/07 §1](07-yak-stvoryty-strategiyu.md) поширюється і на розмову з моделлю.

### 6.5. Мем-коїни та copy-trading

Стаття прямо описує, як алгоритмічних копітрейдерів експлуатують через «наївне
пакетування»: KOL створює токен і сам викуповує його в тому ж блоці, копі-боти
заходять слідом, маніпулятор продає. **Не будувати агента, що сліпо копіює гаманці**
без детектора маніпуляцій (кластеризація адрес, графові ознаки, перевірка
синхронного виконання). Поза скоупом lab.

### 6.6. Prompt injection із зовнішніх даних

Якщо LLM-контур читає веб, новини, твіти чи дані з мережі — ці тексти можуть містити
інструкції. Контент ≠ інструкції: вхідні дані ніколи не розширюють прав агента,
інструменти — за allowlist, небезпечні дії — з підтвердженням людини.

### 6.7. Ключі та безпека

У lab це вже вирішено правильно: `TRADING_MODE=research`, `LIVE_ENABLED=false`,
`lab live` завжди падає (fail closed). Якщо колись live — окремий контур, окремі
ключі, малий ліміт, і поведінка агента, яку можна зупинити однією командою.
Стаття пропонує для цього TEE (апаратні анклави) — але сама ж наводить дослідження
кінця 2025 року, де обладнанням за ~$1000 витягли ключі з ланцюжка атестації Intel.
«Математичний доказ» теж має модель загроз.

### 6.8. Недетермінізм і вартість

Той самий промпт → різні відповіді. Тому промпт, модель і дата зберігаються разом із
артефактом. І рахуй вартість: якщо 200 гіпотез дали 0 прийнятих, дешевше звузити
простір пошуку, ніж збільшувати кількість спроб.

### 6.9. «Звучить переконливо» ≠ «працює»

Стаття сама підсумовує: технологічний арсенал не гарантує прибутковості, а головний
виклик — не здатність мережі знайти патерн, а архітектура управління ризиками. Модель
дуже переконливо пояснює, чому стратегія мала б працювати. Це і є її головна
небезпека: вона знижує відчуття ризику, не знижуючи самого ризику.

## 7. Що можна зробити вже сьогодні в цьому репо

```bash
# 1. Дані (публічні Binance klines, без API-ключів)
uv run lab ingest --start 2025-01-01

# 2. Зафіксувати планку: buy&hold на тому ж OOS-періоді
uv run lab research --robot regime --folds 4

# 3. Подивитись, який промпт піде в модель (мережі не торкається, ключ не потрібен)
.venv/bin/python scripts/propose_alphas.py --dry-run

# 4. Спитати модель і записати артефакт (потрібен LLM_API_KEY у .env)
.venv/bin/python scripts/propose_alphas.py --count 5 --as-of 2026-09-15
#    або локальний сервер відкритих ваг, без передачі даних у хмару:
.venv/bin/python scripts/propose_alphas.py --base-url http://127.0.0.1:11434/v1 --model qwen2.5:14b

# 5. Людський апрув → реалізація в domain/ → ворота
uv run python scripts/train_formulaic_lgbm.py --catalog catalog --output models/formulaic.txt

# 6. Увімкнути робота і порівняти з планкою кроку 2
echo "FORMULAIC_MODEL_PATH=models/formulaic.txt" >> .env
uv run lab research --robot formulaic_lgbm --folds 4

# 7. Опційні ризик-оверлеї (не змінюють сигнали) — по одному, з повторним прогоном
uv run lab research --robot formulaic_lgbm --folds 4   # USE_FRACTIONAL_KELLY=true
```

Після кожного кроку — рядок у [journal.md](../research/journal.md): **що перевірили, яке
число, прийнято чи відкинуто і чому**. Це найдорожчий артефакт усієї роботи.

## 8. Підсумок одним абзацом

Велика міркуюча модель не дає торгової переваги — вона дає **швидкість циклу
дослідження**: формулює гіпотези, пише код за існуючим контрактом, ловить підгляд у
майбутнє, розбирає звіти, веде документацію. Перевага народжується у воротах, через
які проходить кожен її результат: тести → purged K-fold → walk-forward OOS →
реалістичні комісії та проковзування → ризик-шар із fail-closed. Тому правильна
інтеграція виглядає так: **модель ззовні, детермінований код усередині, людина на
апруві, і жодного LLM-виклику в гарячому шляху.** І головна пастка — не в тому, що
модель помилиться, а в тому, що вона вже знає, чим закінчилась історія, на якій ти
збираєшся її перевіряти.

## 9. Що з цього вже реалізовано в репо

Офлайн-контур із розділів 1–4 існує як код. Гарячий шлях не змінився: `lab live`
і далі fail closed, жодна стратегія не імпортує LLM-клієнт.

| Шар | Файл | Роль |
|-----|------|------|
| Domain | `domain/hypothesis.py` | Контракт гіпотези: обов'язкові поля, межі горизонту, нормалізація знаку і лінтер вигаданих ознак (`unknown_identifiers()`) |
| Domain | `domain/formulaic_alphas.py::FEATURE_NAMES` | Публічний перелік 12 ознак — його підставляє промпт і ним перевіряється формула |
| Domain | `domain/ports.py::ChatCompleter` | Порт моделі: завдяки йому цикл тестується без мережі |
| Application | `application/propose_alphas.py` | Промпт → один виклик → валідація → артефакт із provenance |
| Infrastructure | `infrastructure/llm_client.py` | OpenAI-сумісний клієнт на stdlib; без ключа падає закрито |
| Interface | `scripts/propose_alphas.py` | CLI: `--dry-run`, `--count`, `--as-of`, `--model`, `--base-url`, коди виходу 0/2/3 |
| Дані | `research/prompts/`, `research/hypotheses/`, `research/journal.md` | Шаблони промптів, артефакти, журнал рішень |

Що варто знати про поведінку:

- **Артефакт ніколи не перезаписується.** Повторний виклик з тим самим промптом і
  моделлю отримує суфікс `-r2`: недетермінізм моделі не має права стирати історію.
- **У файл не потрапляють облікові дані.** Записується лише хост ендпоінта, навіть
  якщо в `LLM_BASE_URL` був userinfo.
- **Вигадана ознака не блокує артефакт, але позначається.** `count_flagged` і
  `unknown_identifiers` у JSON — це сигнал для рев'ю, а не автоматична відмова:
  рішення ухвалює людина.
- **Промпт версіонується хешем.** `prompt_sha256` у артефакті відповідає на питання
  «який саме текст дав цей результат» через місяці.

Перевірка контуру без мережі (те саме роблять unit-тести):

```bash
.venv/bin/python -m pytest tests/unit/test_hypothesis.py \
    tests/unit/test_propose_alphas.py tests/unit/test_llm_client.py -q
```
